# backend 数据库设计逻辑

本文档基于 `backend/init.sql`、`backend/app/models/*`、`backend/app/router/*` 和 Alembic 迁移整理，用于说明当前真实后端的数据库表设计思路。重点厘清每张表的作用、核心字段和表之间的业务关系。

## 1. 总体设计

当前后端围绕“用户登录 -> 创建会话 -> 上传/解析文档 -> 基于文档聊天 -> 查看历史”这条链路设计数据库。

核心表包括：

| 表名 | 作用 |
| --- | --- |
| `users` | 保存登录注册用户，是业务数据归属的根实体。 |
| `sessions` | 保存用户的历史对话会话，用于左侧历史列表和会话归档。 |
| `messages` | 保存某个会话下的问答历史，包括用户问题、模型回答、引用文档和推荐问题。 |
| `knowledgebases` | 保存用户上传到知识库的文件清单，用于知识库页面展示、重复文件校验和删除。 |
| `document_uploads` | 保存某个会话内快速上传/解析过的文档记录，用于判断当前会话是否有关联文档。 |

注意：代码中还存在 `backend/app/models/knowledgebase.py`，定义的是单数表名 `knowledgebase`，但主业务路由实际使用的是 `models.message.KnowledgeBase`，对应表名为 `knowledgebases`。当前应以 `knowledgebases` 为主。

## 2. users：用户表

### 作用

`users` 是用户身份表，支撑注册、登录和 JWT 登录态校验。

注册时写入该表；登录时根据 `username` 查询用户并校验 `password_hash`；后续接口通过 token 中的 `user_id` 定位当前用户。

### 核心字段

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `SERIAL` / `Integer` | 主键 | 用户唯一 ID。JWT payload 中的 `user_id` 来源于这里。 |
| `username` | `VARCHAR(50)` | 唯一、非空 | 登录用户名，注册时需要保证唯一。 |
| `password_hash` | `VARCHAR(100)` | 非空 | 密码哈希值，不保存明文密码，不返回给前端。 |
| `created_at` | `TIMESTAMP` | 默认当前时间 | 用户创建时间。`init.sql` 中存在，当前 ORM 未显式声明。 |
| `updated_at` | `TIMESTAMP` | 默认当前时间 | 用户更新时间。`init.sql` 中存在，当前 ORM 未显式声明。 |

### 关系

- `users.id` 与 `sessions.user_id` 是一对多关系：一个用户可以有多个会话。
- `users.id` 与 `knowledgebases.user_id` 是一对多关系：一个用户可以上传多个知识库文件。
- 数据库层当前没有显式外键，业务层通过 `user_id` 字段维护归属关系。

## 3. sessions：会话表

### 作用

`sessions` 保存用户的历史对话会话，主要用于前端左侧“历史”列表。

真实 `backend` 的流程比较特殊：`POST /create_session` 只生成并返回 `session_id`，不立即插入 `sessions` 表。用户第一次调用 `POST /chat_on_docs` 并完成模型回答后，`service/core/chat.py` 中的 `update_session_name()` 才会：

1. 查询 `sessions` 中是否已有该 `session_id`。
2. 如果没有，根据用户第一条问题生成 `session_name`。
3. 插入一条会话记录。

### 核心字段

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `session_id` | `VARCHAR(16)` | 主键 | 会话 ID。由 `uuid.uuid4().hex[:16]` 生成，前端路由 `/chat/:id` 使用该值。 |
| `session_name` | `VARCHAR(255)` | 非空 | 会话名称。真实后端通过大模型根据首问生成；mock 可先使用“新对话”。 |
| `user_id` | `VARCHAR(255)` | 非空、有索引 | 会话所属用户 ID。 |
| `created_at` | `TIMESTAMP` | 默认当前时间、有索引 | 会话创建时间，用于历史列表展示和排序。 |
| `updated_at` | `TIMESTAMP` | 默认当前时间 | 会话更新时间。 |

### 索引

| 索引 | 字段 | 作用 |
| --- | --- | --- |
| `idx_sessions_user_id` | `user_id` | 加速查询某个用户的所有会话。 |
| `idx_sessions_created_at` | `created_at` | 支持按创建时间排序或筛选历史会话。 |

### 关系

- `users.id` -> `sessions.user_id`：一个用户拥有多个会话。
- `sessions.session_id` -> `messages.session_id`：一个会话包含多条问答消息。
- `sessions.session_id` -> `document_uploads.session_id`：一个会话可以关联多个快速上传/解析文档记录。
- 当前数据库未定义外键，依靠业务代码按 `session_id` 和 `user_id` 维护关系。

## 4. messages：消息表

### 作用

`messages` 保存会话内的问答历史。每次 `POST /chat_on_docs` 流式回答结束后，后端调用 `write_chat_to_db()` 写入一条记录。

前端进入聊天页时调用 `GET /get_messages?session_id=xxx`，后端按 `session_id` 查询该会话历史，并还原用户问题、模型回答、引用文档、推荐问题和思考内容。

### 核心字段

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `message_id` | `UUID` | 主键，默认 `gen_random_uuid()` | 消息唯一 ID，需要 PostgreSQL `pgcrypto` 扩展。 |
| `session_id` | `VARCHAR(16)` | 非空、有索引 | 所属会话 ID，对应 `sessions.session_id`。 |
| `user_question` | `TEXT` | 非空 | 用户原始问题。 |
| `model_answer` | `TEXT` | 非空 | 模型完整回答。 |
| `documents` | `TEXT` | 可空 | 引用文档/检索片段的 JSON 字符串。`init.sql` 注释提到 jsonb，但当前字段是 `TEXT`。 |
| `recommended_questions` | `TEXT` | 可空 | 推荐问题，通常存 JSON 字符串。 |
| `think` | `TEXT` | 可空 | 模型思考过程或 reasoning 内容。 |
| `created_at` | `TIMESTAMP` | 默认当前时间、有索引 | 消息创建时间。 |
| `updated_at` | `TIMESTAMP` | 默认当前时间 | 消息更新时间。 |

### 代码差异说明

`backend/app/models/message.py` 中 `Message` ORM 仍声明了较旧字段：

- `create_time`
- `retrieval_content`

但 `init.sql`、`history_rt.py` 和 `service/core/chat.py` 实际使用的是：

- `created_at`
- `documents`
- `recommended_questions`
- `think`

因此整理 mock 或继续开发时，应优先以 `init.sql` 和实际 SQL 查询/插入逻辑为准。

### 索引

| 索引 | 字段 | 作用 |
| --- | --- | --- |
| `idx_messages_session_id` | `session_id` | 加速按会话查询历史消息。 |
| `idx_messages_created_at` | `created_at` | 支持按消息时间排序。 |

### 关系

- `sessions.session_id` -> `messages.session_id`：一个会话对应多条消息。
- `messages.documents` 中保存的是引用文档片段的 JSON 文本，不是直接外键。
- `messages` 不直接保存 `user_id`，用户归属通过 `session_id -> sessions.user_id` 间接确定。

## 5. knowledgebases：知识库文件表

### 作用

`knowledgebases` 保存用户上传到知识库的文件清单。它不是向量库本身，也不保存文件内容，只记录“某个用户上传过哪些文件”。

业务用途包括：

- `GET /get_files`：展示当前用户的知识库文件列表。
- `POST /upload_files`：上传前校验同一用户下是否已有同名文件，避免重复上传。
- `DELETE /delete_file/{file_name}`：删除某个用户的知识库文件记录，并配合服务层删除底层文档数据。

### 核心字段

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `SERIAL` / `Integer` | 主键，自增 | 文件记录 ID。 |
| `user_id` | `VARCHAR(255)` | 非空、有索引 | 文件所属用户 ID。 |
| `file_name` | `VARCHAR(255)` | 非空 | 文件名，用于展示、重复校验和删除。 |
| `created_at` | `TIMESTAMP` | 默认当前时间、有索引 | 文件记录创建时间。 |
| `updated_at` | `TIMESTAMP` | 默认当前时间 | 文件记录更新时间。 |

### 索引

| 索引 | 字段 | 作用 |
| --- | --- | --- |
| `idx_knowledgebases_user_id` | `user_id` | 加速查询当前用户文件列表。 |
| `idx_knowledgebases_created_at` | `created_at` | 支持按上传时间排序或筛选。 |

### 关系

- `users.id` -> `knowledgebases.user_id`：一个用户可以有多个知识库文件。
- `knowledgebases.file_name` 与物理文件、ES/RAG 检索数据存在业务关联，但数据库中没有直接外键。
- 与 `sessions` 没有强绑定。知识库文件偏“用户级”，不是“会话级”。

## 6. document_uploads：会话文档上传记录表

### 作用

`document_uploads` 记录某个会话中通过快速解析接口上传过的文档信息。

它服务于这几个接口：

- `POST /quick_parse?session_id=xxx`：快速解析文档后写入上传记录。
- `GET /sessions/{session_id}/documents`：查询某个会话下所有上传文档。
- `GET /sessions/{session_id}/documents/summary`：查询某个会话是否有文档、最新文档和总数。

这张表和 `knowledgebases` 的区别是：

- `knowledgebases` 是用户级知识库文件清单。
- `document_uploads` 是会话级快速解析文档记录。

### 核心字段

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `Integer` | 主键，自增 | 上传记录 ID。 |
| `session_id` | `VARCHAR(16)` | 非空、有索引 | 所属会话 ID。 |
| `document_name` | `VARCHAR(255)` | 非空 | 上传文档名称。 |
| `document_type` | `VARCHAR(50)` | 非空 | 文档类型，如 `pdf`、`docx`、`txt`。 |
| `file_size` | `Integer` | 可空 | 文件大小，单位通常按字节理解。 |
| `upload_time` | `TIMESTAMP` | 默认当前时间、有索引 | 上传时间，用于判断最新文档。 |
| `created_at` | `TIMESTAMP` | 默认当前时间 | 记录创建时间。 |
| `updated_at` | `TIMESTAMP` | 默认当前时间 | 记录更新时间。 |

### 索引

| 索引 | 字段 | 作用 |
| --- | --- | --- |
| `idx_document_uploads_session_id` | `session_id` | 加速查询某个会话的上传文档。 |
| `idx_document_uploads_upload_time` | `upload_time` | 加速获取最新上传文档。 |

### 关系

- `sessions.session_id` -> `document_uploads.session_id`：一个会话可以有多个上传文档记录。
- 当前数据库没有显式外键，服务层按 `session_id` 查询和维护。
- 快速解析的正文内容不存这张表。真实后端会把解析内容放到 Redis，`document_uploads` 只保存元信息。

## 7. 表之间的业务关系图

```text
users
  ├─ sessions
  │    ├─ messages
  │    └─ document_uploads
  └─ knowledgebases
```

含义：

- 用户是业务归属根节点。
- 会话属于用户。
- 消息属于会话。
- 快速解析文档记录属于会话。
- 知识库文件属于用户，不直接属于某个会话。

## 8. mock_backend 实现时的取舍

为了让前端主流程更容易跑通，`mock_backend` 可以比真实 `backend` 更直接：

1. `POST /create_session` 时立即写入 `sessions` 表，默认 `session_name = "新对话"`。
2. `GET /get_sessions` 直接返回当前用户的会话列表。
3. `GET /get_messages` 对新会话先返回空数组。
4. 等实现 `POST /chat_on_docs` 时，再写入 `messages`，并将 `session_name` 从“新对话”更新为用户首问摘要。

这样虽然和真实后端“首次聊天结束后才插入 sessions”的时机不同，但更符合前端调试需要：创建会话后，左侧历史列表能立即看到记录。

## 9. 建模注意点

1. 当前项目大量关系没有使用数据库外键，而是通过业务字段关联。
2. `user_id` 在多张表里是字符串类型，即使 `users.id` 是整数，业务代码也常用 `str(user_id)`。
3. `messages.documents`、`messages.recommended_questions` 存的是 JSON 字符串，不是结构化 JSONB 字段。
4. `init.sql` 与部分 ORM 定义存在不完全一致，mock 和后续开发应优先参考实际路由和 SQL 使用方式。
5. 密码只保存哈希，不应在任何响应 schema 中暴露 `password_hash`。
